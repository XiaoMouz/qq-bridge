# 2026-10-23：健康检查超时触发数据库重置

时间均为上海时间。生产镜像为 `groonga/pgroonga:4.0.9-debian-17`，PostgreSQL 17.11，arm64。

## 现场证据

- 10 月 22 日 22:58 起多次出现 `server process ... exited with exit code 2`，随后 PostgreSQL 断开全部连接并进行恢复。容器主进程未退出，因此 Docker 仍显示容器运行中。
- 10 月 23 日 17:43:02.730，Docker 启动 `/bin/sh -c pg_isready -U qqbridge -d qqbridge`；17:43:05.769，探针结束；17:43:05.772，PostgreSQL 报 PID 2690 退出码 2，并重置全部连接。
- 原配置是 shell 探针、Docker 超时 3 秒、`pg_isready` 默认连接超时也为 3 秒。PostgreSQL 自身是容器 PID 1。
- 同时有查询长时间等待 `DataFileRead`。I/O 等待是现场已有的性能问题，探针超时又将短时卡顿放大成整库重置。容器内存计数没有 OOM，内核日志未发现 OOM、段错误或磁盘 I/O 错误。
- 重置后，PGroonga 日志出现 `pgrn.000010A ... lock failed 1000 times`，消息 INSERT 卡住；账号单写者被占住后，消息、发送状态和媒体完成状态都无法推进。

## 隔离复现

使用同一个镜像，独立临时容器、内存数据库、无网络、无生产数据挂载。

1. 没有 init 时，让 shell 创建一个随后以 2 退出的遗留子进程。它被 PostgreSQL PID 1 收养；进程退出后，数据库打印相同的 `server process ... exited with exit code 2`，重置全部连接。
2. 使用 shell 健康检查，探针自身超时 3 秒、Docker 超时 1 秒。在隔离容器中暂停 PostgreSQL，强制制造探针超时。观察到多个 `pg_isready` 僵尸进程的父进程为 PID 1；恢复 PostgreSQL 后，立即出现相同的退出码 2 和整库恢复日志。
3. 加上 `--init` 后，遗留子进程由 `docker-init` 回收。同样的退出码 2 不再改变 `pg_postmaster_start_time()`。
4. 保留第 2 步的短超时 shell 探针，仅加上 init，再暂停和恢复 PostgreSQL。探针仍失败，但没有遗留僵尸进程，数据库启动时间前后相同，日志中没有退出码 2 的整库重置。

这解释了为什么此前按“数据库子进程收到 SIGQUIT”追查没有结果：日志中的进程可能是被 PID 1 收养的健康检查进程，不能仅凭退出码将其认定为数据库连接进程。

## 修复及恢复

- PostgreSQL 服务启用 `init: true`，让独立 init 负责回收遗留进程。
- 健康检查改成 `CMD` 直接执行 `pg_isready`，不经 shell；探针自身超时 2 秒，Docker 超时 10 秒，避免两个超时在同一时刻竞争。
- 只重建数据库容器并重启服务端，QQ/NapCat 保持在线。
- 服务端暂停、没有业务连接写入时，使用 `pgroonga_command('lock_clear')` 清理崩溃遗留锁，再恢复服务。不要在仍有索引写入进程时清锁。

此修复阻断健康检查超时导致整库重置的路径；它不代表磁盘等待、全量统计查询或其他性能问题已经消除。

## 清理候选查询索引（18:32）

- 当前未配置非负保留天数，也没有 `keep_original=false` 的原件候选，但每日/启动十分钟后的清理查询仍从通用 sha256 索引逐条回表过滤。现场此前曾见查询持续十分钟，本次用 8 秒上限复查仍超时。
- 在线建立部分索引 `media_refs_discarded_sha256_idx ON media_refs(sha256) WHERE keep_original=false`，并验证 `indisvalid=true`。同一查询实测改用 Index Only Scan，读取两个缓存块、Heap Fetches 为 0，执行 0.057 毫秒，blobs 连接分支无需执行。新增迁移 0029 及对应 schema 声明，不改清理或消息同步语义。
- 该结果来自当前空候选、无到期策略的真实场景；不能作为配置到期策略或大量候选时的性能上限。它消除了一个已确认的后台 I/O 来源，不能把它当作所有长延迟的唯一根因。
- 建索引后的五分钟真实消息样本：收到至处理完成中位数约 0.247 秒、P95 1.424 秒、最大 6.921 秒，查询时 pending/failed 均为 0。这是短时样本，并非持续稳定性保证。
