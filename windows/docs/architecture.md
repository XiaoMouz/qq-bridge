# Windows 客户端架构与接口对齐方案

本阶段只整理接口、应用状态、存储与项目依赖。界面继续使用现有实现，不做视觉调整。验收底线是 macOS / iOS 已使用的后端能力；不得以协议生成成功代替业务对齐。

## 已落地的项目边界

| 项目 | 职责 | 允许依赖 |
|---|---|---|
| BetterChat.Protocol | 从仓库 proto 构建 protobuf 类型，保留 int64、oneof、字段存在性 | Google.Protobuf |
| BetterChat.Domain | 编辑器实体、媒体呈现规则等纯逻辑 | Protocol |
| BetterChat.Application | 服务接口、存储事务接口、同步、分页、已读协调、认证及 MVVM 操作状态 | Domain / Protocol；不引用 WinUI、SQLite、HTTP 实现 |
| BetterChat.Infrastructure | Connect 二进制协议、SQLite 与迁移 | Application |
| BetterChat.Core | 兼容旧项目的引用入口，无业务源码 | Infrastructure |
| BetterChat | WinUI 宿主与现有窗口；后续承担组合根和平台适配 | 当前通过 Core 间接引用上述层 |
| BetterChat.Tests | 无窗口测试、假 HTTP、临时 SQLite、异步状态测试 | 当前通过 Core 引用 |

迁移的现有类型暂保留 `BetterChat.Core` 命名空间，避免一次重命名牵动全部窗口代码；程序集边界已生效。新 ViewModel 位于 `BetterChat.Application.ViewModels`。最终移除兼容入口时再统一旧命名空间，不能把命名空间当作实际依赖边界。

`generate-api.ps1` 为全部 8 个服务、80 个 RPC 生成强类型接口和 Connect 实现。应用功能应注入所需的小接口（例如 `IAuthService`），同步暂注入组合接口 `IBridgeApi`。禁止功能代码拼 RPC 路径或创建另一份 DTO。`Subscribe` 保持异步流，不把它当作普通请求或无限增长的集合。

## 对齐基线与验收口径

详见自动生成的 [接口清单](api-coverage.md) 与 [机器可读证据](api-coverage.json)。扫描范围包括 iOS App、通知扩展、QQBridgeKit、macOS App，排除生成文件和测试。当前 65 个 RPC 有 Apple 调用证据；其中 APNs 专用 RegisterPush 按用户要求排除，其余均有 Windows 调用证据。接口和传输仍覆盖全部 80 个。静态覆盖达标不代表应用流程、宿主接入与平台适配全部完成。

每项能力依次验收：

1. 契约：请求、响应、分页游标、optional / oneof、错误码与 proto 一致。
2. 应用流程：存在调用者、取消与失败处理、会话归属和状态收尾；不能只生成一个包装方法。
3. 持久化：需要保存的结果与游标原子提交；重启、重连和多设备更新不丢失。
4. 平台适配：通知、通话、录音等必须接上 Windows 实现，不能只完成 RPC 就标完成。
5. 验证：假服务端与数据库回归测试；需要真实环境的能力另记实机结果。

新增 proto 或 Apple 调用后重新生成清单。`python windows/audit-api.py --require-parity` 会在缺少未获明确豁免的 Apple 基线调用时失败；当前唯一平台豁免是 APNs 专用 RegisterPush。静态证据不能判断完整业务语义，不能通过增加无用调用来消除缺口。

## MVVM 与会话生命周期

已实现 `IUiDispatcher`、基于 SynchronizationContext 的调度器和 `RpcOperationViewModel<TRequest,TResponse>`。操作具有 Idle / Running / Succeeded / Failed / Cancelled 状态、错误、结果、ICommand 和取消入口。一次只接受一个执行；取消后的迟到响应不发布结果；销毁后不再通知绑定。写操作发送后失败或取消采用保守的“结果待确认”状态，避免自动重发造成重复动作；发送前取消不产生这一状态。

这个原语只负责一次操作，不负责分页、同步、身份、事务或通话状态机。现有窗口尚未整体迁入 MVVM。后续具体 ViewModel / 用例边界如下：

| 功能 | 应用层所有者 | 状态与完成条件 |
|---|---|---|
| 登录、恢复、退出、设备管理 | SessionCoordinator / AccountViewModel | SignedOut → Authenticating → Ready / Expired；恢复失败不能进入已登录状态 |
| 会话、联系人 | DialogListViewModel / ContactsViewModel | 从本地快照读取，服务端差量落库后局部更新；列表分页与刷新状态独立 |
| 聊天、历史定位、发送、已读 | ChatViewModel / MessageRepository / OutboxCoordinator | chatId 固定作用域；历史窗口、草稿、发送状态分别管理；切换会话取消旧加载 |
| 搜索、共享媒体、提及、反应用户 | 各自分页 ViewModel | 请求条件和游标绑定同一 generation，旧结果不能覆盖新条件 |
| 存储、贴纸、群资料、管理员操作 | 独立功能用例和 ViewModel | 写操作成功后刷新对应记录；保留失败状态供显式重试 |
| 通话、通知、录音 | CallCoordinator / 平台接口 | 通话由服务端状态与 Subscribe 驱动；所有结束、拒绝、替换、超时路径释放资源 |

上述具体协调器和大部分 ViewModel 是迁移设计，尚未全部实现，不能视为现成功能。新 ViewModel 不得依赖 Window、DispatcherQueue、SqliteConnection 或 ConnectClient；平台调度器由宿主注入。

SessionCoordinator 应拥有一组 API、存储、同步任务、媒体任务和页面取消令牌。退出时先取消整个 session、等待任务收尾，再关闭库和凭据；新 session 使用新的 generation。账号切换后，旧请求即使完成也不能写新账号的数据库。页面取消只能停止页面加载，不能停止整个账号的同步。

认证入口始终是用户名和密码调用 Login。密码不持久化，服务端返回的设备凭据交给 DPAPI 适配器保存，不能要求用户手工提供设备令牌。登录请求使用无旧认证头的传输；当前调用者已这样构造，后续组合根也必须保持。认证失效必须上报会话状态，而不是在同步中永久重试。

## 本地存储和同步

已实现 `ILocalStore` 事务边界与 SQLite 适配器：WAL、records / cursors、消息窗口读取、pending 发件箱、历史快照、版本防回退。记录与 pts / chat_pts 在同一事务提交；翻历史不推进同步游标；tooLong 清除受影响历史窗口但保留待发送记录。

新增 schema v1：用 `PRAGMA user_version` 标识。既有无版本数据库原样迁入 v1，迁移和版本更新放入同一事务；高于支持版本时拒绝打开，不尝试降级。后续每个 schema 版本必须有独立递进迁移，不能靠删库升级。

`ILocalStore` 是当前兼容接口，仍同步返回可变 protobuf 快照；它不是最终页面仓储接口。后续拆分原则：

已新增 `IChatReadRepository` 与 `LocalRepository`：会话、联系人、消息/事件窗口读取在有界队列的单个后台消费者上执行，队列满时异步等待。窗口键在入队前复制，查询结果为独立 protobuf 对象。`HistoryWindow` 提供对应异步读取入口。排队任务取消后不执行查询；已经执行的 SQLite 查询不会被强行打断，结束后丢弃取消结果。关闭时拒绝新任务，排空已接收任务后才释放自有存储；默认借用存储时由 session 在仓储关闭之后释放。消息与事件的两次读取仍是独立快照，并非跨查询事务。

现有窗口尚未切换到异步仓储，同步写入也尚未纳入统一后台队列，因此这项基础实现不等于 UI 卡顿已经解决。

- 页面只消费异步的 Dialog / Contact / Message / Draft / Outbox 仓储；所有 SQLite 读取、protobuf 解码、索引更新放入串行后台执行队列。不能在 UI 调度器中执行整库查询。
- 同步写入仍走单一事务入口。数据提交成功后才发布带实体类型、chatId 和 revision 的变更通知；全局 Changed 只保留兼容桥，禁止每条消息触发所有页面重建。
- 消息页按 chatId、seq 范围或显式窗口键读取；搜索命中的孤立缓存不能改变历史分页边界。集合按稳定 ID 更新，分页与观察合并更新通知。
- 库按规范化服务器身份和稳定账号标识隔离。当前缓存路径仍受设备凭据影响，凭据轮换迁移需要单独实现；不得直接合并不同账号旧库。
- 草稿、pending、outbox 与媒体缓存分别定保留策略；缓存清理不能删除未发送附件。失败发送重试复用 client_random_id，不能重新生成导致重复消息。
- 数据库关闭必须等待后台队列排空；不要边 dispose 边执行请求。迁移失败保持旧版本与数据可恢复。

同步维持 GetState → GetDifference → 会话补差 → Subscribe。断线按已提交游标续传；流中的临时 typing / mediaReady / call 不推进持久化游标。已加载会话的补差已接入 GetChatDifferences：每批最多 100 个，置顶、未读优先，非 final 或仍落后于已知目标的结果继续单会话分页；省略的会话不推断为删除，重复和未请求的结果不应用。首次会话预取与当前会话优先调度仍待实现。tooLong 必须显式标记历史空洞，不能把不连续的缓存当连续历史。

这意味着当前基础拆层没有解决全部卡顿：同步的全局通知、主线程存储访问、窗口代码中的投影，以及首次加载等待策略仍需按上述边界迁移。测试中的合成缓存读取计时只证明窗口查询减少解码，不能代替真实群聊性能验收。

## 迁移顺序和验证

先完善 session / 后台存储队列和类型化通知，再迁出会话、消息、联系人 ViewModel；随后完成上表全部业务缺口和平台适配。最后把宿主收敛到创建服务、导航和绑定，删除兼容 Core 入口。每一步保持旧宿主可构建，并通过假 HTTP / 临时数据库测试，不要求重启用户正在使用的客户端。

基础验证命令：

```powershell
./windows/generate-api.ps1
python windows/audit-api.py
dotnet run --project windows/BetterChat.Tests
dotnet build windows/BetterChat -p:Platform=x64 -p:OutputPath=bin/architecture-validation/
```

发布验收还须执行严格对齐检查、全部缺口的流程测试及真实设备性能验证。当前阶段未达到这些门槛。

## 联系人 MVVM 落地进度

`ContactsViewModel` 已使用 `IContactService` 和异步本地读取仓储：先显示缓存中的好友与群，再并行获取完整好友/群列表。手动刷新先调用 RefreshContacts，成功后重新加载；普通加载不触发 QQ 强制刷新。任一列表失败保留旧快照，好友分组按返回顺序保存，特别关心不会从原分组移除。取消或销毁后不发布迟到响应，包括响应已进入 UI 调度队列但尚未执行的情况。

ListFriends、ListGroups、RefreshContacts 已有应用层调用和测试，但窗口尚未绑定此 ViewModel，好友分组已随完整列表快照持久化，可在离线重开时恢复。静态调用覆盖不代表端到端功能全部对齐。

## 联系人缓存的事务边界

`IContactDirectoryCache` 由 `LocalRepository` 实现，与异步读取共用一个有界后台队列。原 `ChatReadRepository` 因开始承载缓存写入，更名为 `LocalRepository`。好友（含分组）和群列表以两条独立类型的 protobuf 记录保存在现有 records 表内，使用同一事务提交，无需修改表结构；读取也在同一存储锁内取得完整配对。列表快照不修改全局 pts、chat_pts 或同步 peer 记录。同步重置会清除它，下次重新加载。

ViewModel 优先恢复完整缓存；没有快照的旧数据库回退到同步 peers。在线两个列表都成功后才保存新快照，失败保留旧快照。后台写入开始之后的取消无法撤销已经提交的事务，但不会发布取消结果；这一缓存属于创建它的 session，宿主仍须遵循先取消、排空任务、后关闭数据库的生命周期。

测试通过 SQLite trigger 在第二份列表写入时制造失败，验证第一份列表也回滚；关闭再打开数据库后，在网络失败条件下验证好友、群、特别关心分组与原 pts 均保留。当前窗口尚未绑定新 ViewModel，不能据此宣称用户当前界面的离线体验已完成。

## 聊天子功能 MVVM 落地进度

`MentionsViewModel` 固定绑定 chatId，合并 ListUnreadMentions 与新到消息，按 seq 去重、保留 flags 组合并倒序呈现；@全体成员开关只过滤呈现，不丢弃其已加载记录。显式调用 MarkMentionsSeen 成功后才移除对应条目，changed=false 同样视为服务端已确认。失败保留条目供重试，取消不假定服务器已撤销；确认集合阻止迟到的列表重新加入已确认项。普通消息已读与提及已读没有混用，撤回消息移除，其他会话消息不会进入当前列表。

`ReactionUsersViewModel` 固定绑定 chatId / seq / emojiId，每个目标独立拥有操作状态。名单按 user_id 去重，缺名字时显示完整 64 位号码；刷新失败保留已有名单。没有自行添加协议未定义的分页参数。

两者已具备应用层实现和假服务端测试，尚未与窗口绑定。提及的 Subscribe 消息入口、可见区域确认、跨设备计数更新和弹窗生命周期仍需要宿主接入；名单未接入订阅失效机制，当前由显式加载更新。接口静态检查不是这些端到端行为的验收证明。

## 共享媒体分页落地进度

`SharedMediaViewModel` 固定会话、媒体种类、发送者和排序条件，调用 ListSharedMedia；条件改变时宿主需要创建新实例并销毁旧实例。默认时间倒序用 before_seq，其余排序以及 sender_id 非零的查询使用 offset（已对照服务端 interactions.sharedMedia 实现，发送者筛选的这一行为比 proto 的排序注释更具体）。

同消息多媒体以 seq、kind 和 MediaInfo.ord 区分；重叠页更新已有条目而不是添加重复项，不按 seq 单独去重。未知媒体段保留 protobuf 内容作为回退键。空页只要游标推进仍可继续；没有游标结束，重复/回退游标停止并给出分页错误，网络错误保留原游标供显式重试。没有额外下载媒体文件。

假服务端测试已验证多图不丢失、重叠更新、重复游标停止、发送者筛选的 offset、空页推进及失败重试。窗口绑定、筛选控件及媒体预览入口仍未迁入这个 ViewModel，未完成端到端验收。

## 会话偏好 MVVM 落地进度

`DialogPreferencesViewModel` 固定 chatId，分别提供置顶、通知策略和 @全体成员提醒命令。通知策略仅编码 proto 规定的 default / all / mentions / muted / archived，@全体成员开关不会顺带改变普通通知策略。

这些 RPC 只返回 changed，没有新的 dialog_pts。因此命令状态只表示请求完成；实际属性由 `ApplyDialogAsync` 接受更高版本、同一会话的同步快照更新，不把本地期望值伪装成服务端快照写库。失败不回滚或覆盖同步已到达的新状态，changed=false 仍是成功响应。取消写请求的结果未知状态由共用操作模型表达。

测试验证全部策略编码、跨会话过滤、旧版本过滤，以及 RPC 等待期间收到新同步状态后迟到响应不会将其覆盖。宿主仍需把本地库的会话变更接入 ApplyDialogAsync，并为编辑值、请求状态与实际同步值提供绑定；本轮没有修改窗口。

## 贴纸目录 MVVM 落地进度

`StickerCatalogViewModel` 接入 ListStickers、PrepareStickers 和 AddSticker。准备请求按 MD5 去重并每批最多 60 个，只接受本批请求对应且已有有效 sha256 的返回项；未返回的项作为 Missing 暴露，可显式重试。列表保存描述与商城标记，准备结果仅补充媒体哈希，迟到的未准备列表不会撤销已就绪状态。任一批 RPC 失败时整个操作失败，本次未发布的已完成批次可在重试时从服务端缓存重新取得。

收藏只接受有效的已存储原件 sha256，不自动把缩略图当原件，也不自动重试可能已经成功的收藏请求。成功后设置 NeedsRefresh，由列表重新加载清除；收藏前启动的列表响应不能清除这一标记。尚未准备好的消息图片仍需上层 RequestMedia 流程先取到原件，目录 ViewModel 本身不伪造就绪哈希。

假服务端已验证 61 项分批、重复 MD5、部分准备失败重试、额外响应过滤、格式校验、描述/商城标记保留，以及列表与收藏交错。窗口入口、预览签名与发送操作仍未绑定此 ViewModel，贴纸缓存目前只在实例内存中。

## 会话存储详情 MVVM 落地进度

## 通话状态恢复与 Windows 通知边界

`CallStateViewModel` 接入 GetActiveCall，并提供 ApplyUpdateAsync 供 Subscribe.CallUpdate 接入。恢复请求记录启动时的事件 revision；等待期间收到临时事件时，不发布旧恢复快照。同一通话的结束状态不可逆，已接通状态不被迟到的接听中/响铃状态降级，其他通话的结束事件不清除当前来电。状态对象克隆后发布，不写同步 pts。终态 ID 在 session 实例生命周期内保留。

目前只完成通话状态恢复/合并与假服务端测试。StartCall、AnswerCall、HangupCall、LiveKit 房间连接、音频权限、设备切换和媒体资源收尾尚未实现，不能据此标为可通话。宿主尚未将 Subscribe 事件接入此模型。

已核对 `packages/protocol/proto/qqbridge/v1/auth.proto` 和服务端 `authService.registerPush`：RegisterPush 是 APNs 专用接口。按用户明确要求，Windows 不注册 APNs，不扩展 WNS 或后台推送协议；运行期间通过 Subscribe 接收事件，再交给 Windows 原生通知适配器。该接口作为明确的平台豁免单独记录，保留生成契约与传输，不伪造调用。程序完全退出后的通知不在当前范围。原生通知适配器现已接入 AppNotificationManager；实际通知显示与点击仍待实机验收，不能将静态接口覆盖作为通知已可用的证据。

通知分层约定：应用层负责提醒策略、消息去重及当前会话抑制；Windows 宿主实现通知显示和点击激活，再把 chatId / seq 导航意图交回应用层。同步补差与历史加载不能逐条触发新消息通知，退出账号时停止事件订阅并清理该账号的通知关联。

## 好友删除与联系人缓存修订

LocalStore 的联系人修订号在快照保存和同步重置时递增；在线列表在请求前记录修订，落库时比较后原子提交。其他实例中较早启动的列表不能覆盖删除之后的缓存。修订号属于同一个 session 的 LocalStore 实例，不作为跨进程并发协议；组合根必须为账号复用同一个存储实例。没有旧完整快照时沿用同步 peers 构造缓存再移除目标，等待后续完整列表刷新。

## 通话命令编排落地进度

`CallCoordinator` 接入 StartCall、AnswerCall、HangupCall，并依赖可注入的 ICallAudioSession。PrepareAsync 先检查权限和设备，成功后才呼出/接听；连接凭据只传给音频适配器，不成为 ViewModel 公开结果。一个协调器串行管理一个本机音频会话，已在本机入会时拒绝再发起另一通。

服务器已返回通话 ID 后，入会失败或取消会尝试挂断已知通话，并以独立超时释放音频；两种收尾都尝试，错误聚合上报。收到结束临时事件时记录终态并取消该通话的入会任务；即使适配器忽略取消后才返回，仍释放音频。挂断 RPC 失败也会释放已连接的本机音频，不伪造服务器结束状态。

若呼出 RPC 结果丢失且未取得 call_id，协调器不能猜测应挂断哪通；宿主必须使用活动通话恢复和明确错误状态处理，不能自动重拨。退出 session 的挂断策略、跨设备接听冲突、音频连接状态通知和生命周期组合仍待完善。

## 账号作用域组合根

`ClientSessionRuntime.CreateAsync` 在后台打开和迁移 SQLite，并组合传输、仓储、同步、联系人及通话状态 ViewModel。Start 幂等启动同步；Subscribe 临时通话事件通过可等待回调按序交给通话状态。DisposeAsync 先取消生产者，等待同步和已归属的 ViewModel 操作收尾，再排空仓储队列、关闭数据库与传输；重复关闭等待同一任务。通用操作支持异步排空，避免已确认的缓存回写与关库竞争。

该组合根尚未接入现有 WinUI 宿主，也未管理全部页面 ViewModel、CallCoordinator 或通知适配器。通过公开 Api 独立发起的调用须由调用者管理生命周期。宿主关闭时须保持 UI 调度器可用并异步等待，不能在 UI 线程同步阻塞。测试覆盖忽略取消的操作排空、Subscribe 通话状态路由、重复启动与关闭及关闭后访问拒绝；未据此宣称现有窗口已消除卡顿。

## 全局补差异常保护

GetDifference 按请求发出前的全局 pts 验证响应：非末页必须推进，末页允许游标不变但不能回退；缺失 Difference 视为协议错误。响应到达时本地 pts 已变化，则丢弃旧响应并按当前游标重取，旧 tooLong 不得清库。合法的过期游标仍重置缓存并从 0 拉取，保留 pending 幂等 ID；若从 0 拉取仍返回 tooLong，则退出本次补差并走现有退避重试，避免无间隔请求和重复清库。

已核对服务端 sync/difference.ts：当前 horizon 判断位于全量查询前，因此 horizon 大于 0 时存在全量请求仍返回 tooLong 的路径。Windows 此处只防止空转，不声称修复该服务端全量恢复条件，也未改动后端。假服务端测试覆盖坏页不应用、退避触发、重复过期停止及迟到清库保护；真实网络恢复与大群性能仍须独立验收。

## 消息渲染的后台快照

HistoryWindow.Capture 固定本次查询的消息序号、事件 ID、实时追加边界及是否包含待发送项；之后翻页修改窗口不会改变已发出的查询。LocalRepository.GetTimelineAsync 在后台执行，LocalStore 在同一锁内读取消息、事件、pending 和 outbox，避免发送确认从 pending 移入 outbox 时读到两份不一致状态。定位窗口不附带最新消息和待发送项。

WinUI 消息渲染改用该快照，通过单个渲染任务合并重复刷新。结果返回后检查账号运行时、窗口对象、chatId、刷新修订号及取消令牌；旧结果不更新当前页面。初次加载在渲染完成后再定位滚动目标。假数据测试覆盖窗口捕获后翻页不污染旧查询、搜索孤岛隔离、发送确认转换、定位页隔离及结果可变对象与数据库分离。

## 发送与重试的运行时接入
