# 附件重试与发送幂等复核（2026-10-15）

## 问题与修改

此前发件箱的 `Sender.resend` 已沿用原 ID，但聊天页附件失败后再次点击发送，仍会走 `Sender.send` 的默认随机 ID。服务端已接收而 RPC 回包丢失时，同一附件可能产生第二次发送。该路径由 Mac 与 iOS 共用。

Attachment 现在生成并持有固定 clientRandomId；上传成功后保存已准备的 segment 与引用。附件条失败重试沿用它们，不重复上传已经成功的媒体，也不将输入栏后来选择的引用覆盖到已提交请求。重新选择同一张图会创建新的 Attachment，仍可正常发送两次。上传失败尚无准备结果时允许继续上传。

发送动作从 ChatScreen 提取为 AttachmentSending，上传和网络请求由 SessionAttachmentSendingService 适配；视图仍负责批次启动和滚动。返回值明确表示是否用掉本批次的引用：重试使用旧引用 42，不会误清本批次新选的引用 99。视频和文件继续不携带引用。手机没有移除任何功能；这是共享可靠性修复。

## 验证

六项附件测试与五项 Mac 草稿测试共 11 项通过：`/tmp/betterchat-attachment-retry-final-tests.log`。附件测试使用真实 Sender、内存 LocalStore、可控 API 和上传替身，不连接账号或发送真实消息。

- 服务端替身先接收消息再丢回包，跨草稿移交后重试的两次请求完全一致；只记一次投递，上传一次。
- 先从发件箱重试，再从附件条重试，三个请求沿用同一 ID，只记一次投递。
- 上传失败保留引用，迟到进度不能把失败状态改回上传中；重试重新上传。
- 文件、视频均不使用或消耗引用（同一参数化测试的两种情况）。
- 相同内容重新选择两次，具有不同 ID，仍产生两条消息。
- 图片正确消耗匹配的引用；已从草稿移除的附件不能再次发起发送。

Mac 测试构建、iOS 模拟器构建（`/tmp/betterchat-attachment-retry-final-ios.log`）、Mac 严格签名和差异格式检查通过。Package.resolved 未变。普通应用已重新启动至 Something，搜索和输入为空，没有附件或弹窗残留。本轮不将隔离测试冒充真实断网、强退或上传端到端验收。

## 尚未覆盖 / 既有边界

- 附件条和发件箱仍各自显示失败状态；从一个入口重试成功后，另一入口的显示可能等待用户操作。稳定 ID 能避免再次操作导致重复投递，但不等于两个入口的 UI 已自动协调。
- 附件条再次调用 Sender.send 可能更新 pts=0 本地失败条目的 createdAt；发件箱 resend 则保留原时间。
- 同批首张失败、后续图片成功时，原策略允许后续图片使用引用；失败附件仍保存其引用，之后重试可能同样带引用。这是本次提取前已经存在的策略，本轮未改成“失败也占用引用”。
- 重试开始后旧上传进度晚到仍可能短暂影响进度显示；失败终态不受影响。
- 草稿仅进程内保存，退出后未获确认的发送由已有持久化发件箱恢复；没有新增附件草稿跨重启保存。

Claude Code（Opus 5.5、auto）最终复核确认本次请求冻结与跨入口去重无阻塞缺陷。第一次提出的旧引用消耗新引用问题已修正；批次失败后的引用保留是本轮开始时工作区已有行为，不以更早 Git HEAD 混作起点。详见 [Opus 复核](OPUS_ATTACHMENT_RETRY_REVIEW.md)。


## 后续：附件条与发件箱确认同步（2026-10-15）

上文“双入口显示不协调”和“重试改变首次时间”已补实现与隔离测试，下面为当前状态。

- 本地库新增按会话与附件 ID 观察发件箱的接口，包含 sent 终态。附件条按记录显示重试中 / 失败，只有明确 sent 才移除；空结果或其他会话记录不代表成功。
- ChatScreen 的独立 AttachmentOutboxObserver 随页面出现、草稿队列更换、附件集合或批次运行状态变化重订阅。离开期间的完成由新订阅的首个快照补齐，不轮询。
- 当前批次由发送动作管理状态，避免旧失败快照覆盖新尝试；批次结束后重读。同步已确认成功时，晚到的 RPC 错误不重新弹失败提示。
- 附件错误带来源 ID；成功只清对应附件错误，不清后续文字或其他附件的错误。
- Sender.send 收到已有 ID 时核对会话、内容与引用，沿用原条目重试，保留首次时间；若本地已知 sent，直接返回，不请求网络、不降级记录。内容不一致则拒绝，不覆盖原请求。

## 后续：上传回调按尝试隔离（2026-10-15）

上文“旧上传进度跨重试晚到”的边界已进一步处理。此前仅检查附件处于 uploading，旧回调会把新重试的 25% 改为 95%；已在生产发送动作的受控延迟测试中复现，修正前两项测试共四处断言失败（`/tmp/betterchat-upload-progress-before.log`）。

每次上传现在创建独立的进度接收对象，完成、失败或退出后解除草稿引用；即便回调已经排入 MainActor，也会因接收对象失效而忽略。上传准备成功立即显示 100%，已有上传结果的发送重试保持 100%，不再被原上传回调改回较低值。进度对象弱引用草稿，上传服务意外保留回调也不延长草稿生命周期。仅使用当前附件的原发送 ID，未改变上传重试、引用或发件箱协议。

新增三项检查与发件箱、草稿回归共 **21 项通过**（`/tmp/betterchat-upload-progress-after.log`），iOS 构建通过（`/tmp/betterchat-upload-progress-ios.log`）；Mac 严格签名与差异检查通过，Package.resolved 未变。Opus 5.5 只读确认当次回调归属、完成后的隔离和引用释放，未发现新阻塞问题。仍没有制造真实网络故障或发送测试消息。
